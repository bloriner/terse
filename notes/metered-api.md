# Terse metered execution API — v1 prototype

Date: 2026-10-15. Code: `api/server.py`, `api/client.py`. Tests: `tests/test_api.py` (10 tests).

## The business model

Terse's whole pitch is *fewer tokens per correct program*. A metered execution
API turns that pitch into a price: the customer submits a (Terse, Python) pair
for the same task, the API verifies both produce identical stdout, measures the
token delta with `cl100k_base`, and charges a cut of the inference cost avoided.

**Who pays.** Teams running agentic coding at scale (SWE-agent fleets, internal
dev-tool platforms), and API platforms that resell Terse execution. The buyer
is whoever's inference bill shrinks.

**Why 10%.** `PRICE_PER_TOKEN = $0.30 / 1M` tokens saved — roughly 10% of a
$3.00/1M blended inference price (input+output, mid-tier models, deliberately
conservative). The pitch writes itself: *"you save $9 for every $1 you pay us."*
A take-rate above ~20% invites the customer to just eat the tokens; below ~5%
leaves money on the table for a meter they could build themselves. 10% is the
Schelling point, and it's a module constant precisely so it can move with
measured inference prices.

**Why metering beats flat-rate.** Flat per-seat or per-call pricing charges for
*usage*; metering charges for *value created*. When Terse saves nothing (or the
program is wrong — mismatched stdout is rejected, no savings claimed), the
customer pays nothing. That aligns incentives: we only make money when the
language actually delivers.

## API contract

| Endpoint | Method | Description |
|---|---|---|
| `/meter` | POST | `{"terse_source", "python_source", "stdin_text"?}` → receipt |
| `/receipt/<id>` | GET | stored receipt (404 `receipt_not_found`) |
| `/ledger` | GET | `?limit=&offset=` receipts, newest first |
| `/health` | GET | `{"ok": true}` |

Receipt fields: `receipt_id`, `ts`, `terse_tokens`, `python_tokens`,
`tokens_saved`, `savings_pct`, `price_usd`, `stdout_match`, `method`
(`tiktoken-cl100k` or `char-estimate`), `flags` (e.g. `anomaly: savings_pct >
90`, `no-savings`).

Error model: 400 `terse_E###` (structured Terse error codes pass through),
400 `python_failed` / `python_timeout`, 422 `stdout_mismatch` (outputs differ —
no savings metered), 413 `body_too_large` (1 MiB cap).

## Pricing math — worked example

Assumptions: blended inference **$3.00/1M tokens**; a coding agent emits
**~50K tokens per task** (prompt + repair iterations); Terse saves **25%** →
**12,500 tokens saved per task**. Our cut: **$0.30/1M** saved.

| scale | tokens saved/day | our revenue | customer inference savings | customer keeps (90%) |
|---|---|---|---|---|
| 1K tasks/day (pilot) | 12.5M | $3.75/day ≈ **$1.4K/yr** | $37.50/day | ~$12.3K/yr |
| 100K tasks/day (one large customer) | 1.25B | $375/day ≈ **$137K/yr** | $3,750/day ≈ $1.37M/yr | ~$1.23M/yr |
| 1M tasks/day (platform scale) | 12.5B | $3,750/day ≈ **$1.37M/yr** | $37,500/day ≈ $13.7M/yr | ~$12.3M/yr |

Honest read: at pilot scale this is coffee money — the model needs a large
customer or platform distribution to matter. That's fine; the marginal cost per
metered execution is ~zero, so it's pure operating leverage once landed.

Measured on real pairs (v1 sanity check): fizzbuzz bench pair — Terse **39**
tokens vs Python **65** → **26 saved (40.0%)**, price **$0.000008**. The meter
agrees with `bench/run.py` to the token.

## Honest limitations

1. **v1 meters caller-supplied pairs; it doesn't generate them.** The
   generator today is the agent + MCP server (`terse_eval`/`terse_transpile`).
   The closed loop is a future `POST /solve`: natural-language task in, Terse
   solution out, savings metered against a model-written Python baseline — both
   sides generated by us, which also kills the baseline-gaming problem below.
2. **The Python baseline runs need a real sandbox in production.** v1 uses a
   subprocess with a 5s timeout — no network/fs isolation. Do not expose to
   untrusted callers without nsjail/gVisor/Firecracker in front of it.
3. **tiktoken only covers OpenAI encodings.** Claude/Llama/Gemini tokenizers
   aren't measurable from here (same caveat as `notes/dialects.md`). The
   `method` field on every receipt exists so pricing can be re-based per
   tokenizer later.
4. **Stdout equality is strict.** Programs must print identically; trailing
   whitespace differences count as mismatches. Deliberate — a billing meter
   should fail closed.
5. **Savings are measured on source, not on the full agent trace.** The big
   token spend in agentic coding is repair iterations; Terse's first-try
   validity (GBNF + error protocol) is where the real money is, and v1 doesn't
   meter that. A `/solve` endpoint with attempt-counting would.

## Abuse considerations

**Hardest vector: baseline deflation.** The customer controls the Python
baseline, and every measured saved token is a token they pay for — so the
incentive runs exactly the wrong way: submit minified, golfed, or
machine-compressed Python as the "baseline" and the measured savings collapse
toward zero while they use the execution/meters nearly free. This is worse
than baseline *inflation* (which only raises the customer's own bill and is
self-punishing).

Mitigations, layered:
- **Minification heuristics** at ingest: reject baselines with extreme avg line
  length, single-char identifier density, or char/token ratios far from
  idiomatic code. (Not in v1 — specified here first.)
- **Per-API-key savings distribution monitoring:** flag accounts whose
  receipts cluster at ≤0% savings; legitimate users show a spread.
- **Anomaly flags on receipts** (v1 implements this): `savings_pct > 90`
  flagged for review, symmetric with the deflation case.
- **Contractual baseline definition:** "the idiomatic production code you
  would have shipped" — gives legal recourse, not just technical.
- **Endgame: `/solve`.** When we generate both sides, there is no
  customer-supplied baseline to game. The meter becomes a pure measurement
  instrument, and the business moves from "trust our customers' baselines" to
  "watch us beat them."

Secondary vectors: replaying the same pair (harmless — each meter is a real
execution they'd pay for anyway); stdout-oracle probing to exfiltrate the
Terse-side implementation (low value — the interpreter is open source).
